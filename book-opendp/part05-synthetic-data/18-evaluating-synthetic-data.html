18  Evaluating and tuning synthetic data

Author

Manuel V. Loureiro

Published

Version 2026-10-30

Synthetic data with AIM and MST ended with a synthetic table and a privacy statement. The statement says how little the table reveals about any one person, but nothing about whether the table is any good. The one idea of this chapter is that “good” is three separate questions, and only the release itself can answer the first. You will compare an AIM release with the real data on the marginals it measured, on a table it never measured, and through a classifier trained on its rows. Then you will repeat the comparison at three budgets and for MST, and write down what to publish with the rows.

The documentation stops once the rows are generated, so this chapter goes further, with methods from the AIM paper and a benchmark of synthetic-data generators. The comparison is possible only because the Labour Force Survey (LFS) sample is public. On private data, run the same comparison on a public or historical stand-in before the release, never on the data you protect.

The script opendp_evaluating_synthetic_data.py runs every step on OpenDP 0.16.0 with mbi 1.1.0, and imports the functions it shares with the script of the previous chapter. The budgets, noise scales, thresholds, conversions to the privacy parameter \(\varepsilon\) and the classifier trained on real rows are the same on every run. OpenDP’s noise cannot be seeded, so the releases, the fitted models and every distance to the truth change. The page shows them in blocks and tables marked as one run. The whole script, with four releases, took 55 seconds.

uv run python code/part05-synthetic-data/opendp_evaluating_synthetic_data.py

18.1 What good means

A synthetic table can be judged by three questions, the checks of the benchmark by Tao and coauthors. Do the marginals that the algorithm measured match the real ones? Do queries it never measured come out right, such as a count over all four columns or a share within a small group? And does a model trained on the synthetic rows work on real rows? Each check catches failures that the other two miss.

Only the first question has an error bar from the release. Every measured marginal carried Gaussian noise of a known scale, so the std method of the table says how far its fitted counts should be from the truth (Contingency tables). A table that no measurement covers has no such bar, and std refuses it, and a downstream model has none either. So you can answer the second and third questions only against real data. On a real release, that means public or historical data of the same kind (the full edition’s chapter on public data).

The release under evaluation is the AIM release of the previous chapter with its nulls filled. It has the same privacy unit of 36 contributions (the data and the context), the same four columns with their keys and cuts, and ten rounds. The budget is a privacy parameter \(\rho\) of 0.1 under zero-concentrated differential privacy (zCDP), which bounds the privacy loss on average, with Gaussian noise. A slack \(\delta\) of \(10^{-7}\) pays for releasing the keys of ILOSTAT. Two functions build the context and the query from a budget, so that later sections can change it.

def make_context(frame: pl.LazyFrame, rho: float) -> dp.Context:
    """A context for one release at budget rho, with the previous chapter's unit and slack."""
    return dp.Context.compositor(
        data=frame,
        privacy_unit=dp.unit_of(contributions=CONTRIBUTIONS),  # neighbours add or remove one person's 36 rows
        privacy_loss=dp.loss_of(rho=rho, delta=DELTA),  # zCDP with Gaussian noise; delta pays for ILOSTAT's keys
    )


def table_query(context: dp.Context, rho: float, algorithm: Algorithm) -> ContingencyTableQuery:
    """The previous chapter's query with its nulls filled, at the budget rho, with the algorithm plugged in."""
    return (
        context.query(rho=rho, delta=DELTA)
        .with_columns(synth.fill_nulls())  # every null lands in a public key before anything is counted
        .select(*COLUMNS)
        .contingency_table(keys=synth.KEYS, cuts=synth.CUTS, algorithm=algorithm)
    )

The release is one line. The next line puts the real rows through the same steps as the query, filling the nulls, cutting the numbers into bins and mapping codes outside the keys to null. So every real marginal has exactly the cells of the synthetic one.

aim_query = table_query(make_context(frame, RHO), RHO, dp.mbi.AIM(rounds=ROUNDS))
table_aim, seconds_aim = synth.timed_release(aim_query)
real = synth.binned(frame, table_aim.keys, fill=True).collect()  # the real rows in the table's keys and bins

18.2 The workload error

The first question asks how far each measured marginal of the model is from the real one. The AIM paper calls the average of that distance over a workload the workload error, which AIM itself tries to make small. The distance is the total variation distance of the previous chapter, half the sum over cells of the absolute differences between the shares. It is also the largest difference between the shares that the two tables give to any set of cells. So the worst distance below, 0.00102, means that no question about those columns gets a share off by more than that.

The function below computes it for a list of cliques, the sets of columns that the marginals span. It reads the counts of the model with project_melted instead of drawing rows, because drawing rows adds noise of its own (Section 18.6). Next to each distance it puts the bound of the previous chapter, the distance if every cell of the marginal were off by three standard deviations at once.

def marginal_errors(
    table: ContingencyTable, real: pl.DataFrame, cliques: Sequence[tuple[str, ...]]
) -> list[MarginalError]:
    """Each clique's distance between the fitted model's marginal and the real one, with the table's own standard
    deviation for it and the bound that three standard deviations in every cell would give."""
    errors: list[MarginalError] = []
    for clique in cliques:
        fitted = table.project_melted(clique)  # the model's counts: no rows are drawn
        tv, worst = distance(synth.marginal(real, clique), fitted, clique)
        std = table.std(clique)
        bound = synth.tv_bound(synth.cells(table, clique), std, real.height)
        errors.append(MarginalError(clique, tv, worst, std, bound))
    return errors

Every distance is under its bound by a factor of three or more, and no cell is off by more than a few hundred rows out of 3.8 million. The one-way standard deviations are not the one-way scale of 227.68, because the model combines each one-way measurement with every measured marginal that contains the column. That is why ILOSTAT, which sits in four marginals, gets 201.0.

Read the table as a check of the pipeline, not only of the noise. A distance over its bound means something systematic, such as the nulls of the previous chapter. On private data you cannot fill in this table, because it needs the real marginals. You can fill in the std column, which comes from the release, and that is the error bar you publish.

18.3 A query nobody measured

The second question asks about a table that no measurement covers. The candidates of AIM have at most three columns, so it never measures the four-way table of SEX, AGE, HWUSUAL and ILOSTAT, whose 240 cells hold every combination. The model still answers, with the distribution that agrees with the measured marginals and assumes nothing else (the full edition’s chapter on query release). But the table can no longer put a bar on the answer.

try:
    four_std = f"{table_aim.std(COLUMNS):.1f}"
except ValueError as err:
    four_std = str(err)  # no measured marginal covers all four columns, so the table has no error bar for it
four-way cells: 240  measured by AIM: False
std of the four-way table: attrs (('SEX', 'AGE', 'HWUSUAL', 'ILOSTAT')) are not covered by the query set
four-way (aim rho=0.1, one run): tv=0.00141 largest cell error=450 rows  best measured (SEX, ILOSTAT) tv=0.00022  worst measured tv=0.00102
cells of the share with at least 1,000 real rows: 26
share working by SEX, AGE, HWUSUAL (aim rho=0.1, one run): largest error=2.05 points at {'SEX': 1, 'AGE': '(-inf, 20.0]', 'HWUSUAL': '(1.0, 20.0]'}  real=100.00%  model=97.95%

In this run the four-way table is further from the truth than every measured marginal. Its error comes from the noise of the triples that make it up, and from any dependence of all four columns that no triple shows. Here the four measured triples overlap so much that little is left to guess, so the distance stays near the worst measured one. A release with fewer marginals leaves more to the assumptions of the model, as Section 18.5 shows for MST.

A conditional share is a harder test, because it divides one small count by another. From the four-way table, the script reads the share of people at work in the 26 combinations of SEX, AGE band and HWUSUAL band with a thousand real rows or more. The largest error in this run was two points, for men under 20 who usually work 1 to 20 hours. Everyone in that cell works, since usual hours imply a job, but the model gave it a share of 97.95%. Noise is added per count, not per person, so a small group gets the largest relative error. If an analyst will ask about small groups, measure them, for example with Fixed inside Sequential.

18.4 Train on synthetic, test on real

The third question is whether a model trained on the synthetic rows works on real rows, which the benchmark calls “train on synthetic, test on real”. The task is to predict whether a person works, ILOSTAT equal to 1, from SEX, the AGE band and the HWUSUAL band. The model is a logistic regression from scikit-learn on eleven indicator columns, one per key of each feature.

The script draws 200,000 synthetic rows with method="sample", independently from the model, as a sample from the population would be. It also takes 400,000 real rows in one seeded Polars shuffle. The first 200,000 train the yardstick, a model on real rows, and the rest score both models.

rows = synth.synthesize(table, seed, rows=ROWS, method="sample")  # independent draws from the model
rows = synth.binned(rows.lazy(), table.keys, fill=False).collect()  # the numbers back in their bins
model = classifier(rows, table.keys, seed)  # train on synthetic
def classifier(train: pl.DataFrame, keys: dict[str, Any], seed: int) -> LogisticRegression:
    """A logistic regression that predicts ILOSTAT == 1 from SEX, the AGE band and the HWUSUAL band, fitted on
    `train`, which is either synthetic rows or real rows."""
    return LogisticRegression(max_iter=1000, random_state=seed).fit(design(train, keys), labels(train))


def accuracy(model: LogisticRegression, test: pl.DataFrame, keys: dict[str, Any]) -> float:
    """The share of the held-out real rows the model labels correctly."""
    return float((model.predict(design(test, keys)) == labels(test)).mean())

features: 11 indicators

train on real, test on real: accuracy=0.9313
standard error of an accuracy on 200,000 rows: 0.0006
train on synthetic (aim rho=0.1, one run), test on real: accuracy=0.9313  gap=+0.0000  mean probability difference=0.0015

The model trained on real rows labels 93.13% of the held-out rows correctly, against 39.76% working. The model trained on synthetic rows scored the same in this run, so the gap is zero, well inside the standard error of 0.0006. The test allows a gap of one percentage point, the size of gap that a model would show if it got a few small cells wrong.

But accuracy is a coarse check, because two models that put the probability of every cell on the same side of one half make the same predictions. So the script also reports the mean difference between the predicted probabilities of the two models, 0.0015 in this run. For a single model, fitting it privately and directly (Statistical modelling) is often better than training on synthetic rows.

18.5 What the budget and the algorithm buy

Tuning means running the evaluation under different settings and choosing between them. The script repeats it with AIM at a fifth of the budget, \(\rho = 0.02\), and at five times it, \(\rho = 0.5\), then runs MST at the original budget. Each release gets a context of its own, because you would publish only one of them. Released from the same private data, the four would compose to \(\rho = 0.72\), so tuning on private data spends budget too. Tune on a public stand-in, and release once.

mst_query = table_query(make_context(frame, RHO), RHO, dp.mbi.MST())
table_mst, seconds_mst = synth.timed_release(mst_query)
mst_eval = evaluate("mst rho=0.1", table_mst, seconds_mst, real, test_real, baseline, seed)

aim rho=0.5: oneway scale=101.8234 threshold=630  scale of a round's marginal=169.7056  epsilon at delta=1e-07: 5.6709
mst rho=0.1: oneway scale=227.6840 threshold=1364  scale of a pair=207.8461  epsilon at delta=1e-07: 2.3484
mst rho=0.1 measured: ('HWUSUAL', 'ILOSTAT') std=207.85

budget the four contexts add up to if all were released from the same data: rho=0.72

The scales follow the formula of the previous chapter, the sensitivity of 36 over the square root of twice the budget. So twenty-five times the budget divides every scale by five, from 509.12 to 101.82 for the one-way marginals. In \(\varepsilon\), the smallest budget is 1.00 and the largest 5.67 (the full edition’s chapter on choosing epsilon discusses which a release can defend).

The budget buys accuracy everywhere, but not evenly. Across the three budgets, the worst measured marginal and the four-way table improve steadily, though less than the scales shrink. The one-way marginals, already close at \(\rho = 0.1\), improve least. The share error falls fastest at the low end, from 15.64 points to 2.05, because small groups are the first to drown in noise. A larger budget also lets AIM measure more marginals, four, five and six in this run. All four classifiers scored the same accuracy of 0.9313, so for this task the budget makes no visible difference.

The algorithm changes more than the budget does. MST measures three pairs, all with ILOSTAT in this run, so it treats SEX, AGE and HWUSUAL as independent once employment status is known. That is false, since hours depend on sex and age among those who work. So its four-way table is tens of times further from the truth than that of AIM at the same budget.

The share error of MST reaches 24 points, for women under 20 who report at most one usual hour. The predicted probabilities move by 0.028 on average, but the accuracy still does not change. MST is the better choice when the questions are about pairs and the release must be fast, 3.3 seconds against 13.7 for AIM in this run.

The cuts and the number of rounds are the other two settings. Finer cuts multiply the cells of every marginal, each with noise of the same scale, so the bound on each marginal grows. More rounds give each round a smaller share, so AIM measures more marginals, each less precisely.

18.6 How many rows, and how to draw them

The evaluation of the marginals read the model, not the rows, because drawing a fixed number of rows independently adds a sampling error to the error of the model. The script computes its expected size for each one-way marginal from the shares of the table, at 200,000 rows and at the size of the real table.

sampling noise on one-way SEX: expected tv at 200,000 rows=0.00090  at 3,811,932 rows=0.00021
sampling noise on one-way AGE: expected tv at 200,000 rows=0.00152  at 3,811,932 rows=0.00035
sampling noise on one-way HWUSUAL: expected tv at 200,000 rows=0.00100  at 3,811,932 rows=0.00023
sampling noise on one-way ILOSTAT: expected tv at 200,000 rows=0.00140  at 3,811,932 rows=0.00032
aim rho=0.1 one-way tv summed (one run): model=0.00029  round=0.00028  sample=0.00745
aim rho=0.1 four-way tv (one run): model=0.00141  round=0.00139  sample=0.00483
mst rho=0.1 four-way tv (one run): model=0.05610  round=0.18410  sample=0.05791
mst rho=0.1 pair ('AGE', 'HWUSUAL') tv (one run): model=0.01504  round=0.12370  sample=0.01261

At 200,000 sampled rows the sampling error of SEX is many times the model error of Table 18.1, so the rows are much worse than the release. Even at the size of the real table the sampling error stays above the model error, because the privacy noise at this budget is small against 3.8 million rows.

The default method="round" avoids the sampling error, and for AIM its marginals matched those of the model in this run. But in mbi 1.1.0 it draws each column by the rank of a row within the group of its parent columns. So two columns with the same parents are sorted together, which ties them. The star of MST makes AGE and HWUSUAL such a pair, and rounding moved their marginal from 0.01504 to 0.12370, while sampling left it near the model. So sample when the joint distribution of the rows matters, and draw as many rows as the total of the model if the marginals must be close. Check the pairs before you trust rounded rows.

18.7 What to publish

A synthetic dataset needs a statement of its guarantee and enough description for a user to judge what it can answer. The practitioner edition’s chapter on release and governance builds such a statement for a trained model, and the same rules apply. The numbers come from the variables of the script, and the statement names what was public.

print(
    f"This synthetic dataset of {ROWS:,} rows was generated by AIM (OpenDP {dp.__version__}, mbi "
    f"{importlib.metadata.version('mbi')}, rounds={ROUNDS}, queries up to 3 columns) from one contingency table "
    f"over {', '.join(COLUMNS)} released under (rho = {RHO:g}, delta = {DELTA:g})-zero-concentrated differential "
    f"privacy, which is (epsilon = {epsilon:.2f}, delta = {2 * DELTA:g})-differential privacy, for adding or "
    f"removing all of one person's survey responses, at most {CONTRIBUTIONS} of them, under the central model. "
    f"The keys of SEX and the cuts of AGE and HWUSUAL were fixed in advance; nulls were recoded to "
    f"{synth.FILL}; the keys of ILOSTAT were released with a threshold of {aim_query.oneway_threshold}. "
    f"Drawing the rows by independent sampling is post-processing and spent nothing."
)
This synthetic dataset of 200,000 rows was generated by AIM (OpenDP 0.16.0, mbi 1.1.0, rounds=10, queries up to 3 columns) from one contingency table over SEX, AGE, HWUSUAL, ILOSTAT released under (rho = 0.1, delta = 1e-07)-zero-concentrated differential privacy, which is (epsilon = 2.35, delta = 2e-07)-differential privacy, for adding or removing all of one person's survey responses, at most 36 of them, under the central model. The keys of SEX and the cuts of AGE and HWUSUAL were fixed in advance; nulls were recoded to {'AGE': 0.0, 'HWUSUAL': 99.0}; the keys of ILOSTAT were released with a threshold of 1364. Drawing the rows by independent sampling is post-processing and spent nothing.

The statement covers the rows without a further term, because drawing rows from a released model is post-processing, which cannot weaken the guarantee (the full edition’s chapter on properties). It covers this one table only, and the other releases of this chapter, from the same people, would add to it.

The last row is the one most often done wrong. A distance computed on the private data depends on that data, so publishing it is a new release that the statement does not cover. As Limitations and troubleshooting put it, the guarantee covers what passes through a measurement and nothing computed beside it. The error bars from std are safe to publish, and the distances in this chapter were safe only because the data are public.

This is the last chapter of the book. You can now release statistics, tables, models and synthetic rows through a context. You can also measure their quality on data you may look at, and publish them with a guarantee that says what it covers.
