25  Choosing an accountant

Author

Manuel V. Loureiro

Published

Version 2026-10-30

25.1 Why this matters

You report a model trained with differential privacy (DP) with a privacy level \(\varepsilon\) and a small slack \(\delta\). The code that computes \(\varepsilon\) is an accountant, and the same run can get 6.24 from one accountant and 24,379.55 from another. Table 25.1 runs three accountants on one run of private stochastic gradient descent (SGD), called DP-SGD. They are advanced composition, Rényi differential privacy (RDP) and the privacy loss distribution (PLD). Each record joins each batch with probability \(q = 0.01\), the sampling rate. The noise multiplier \(\sigma\), the noise as a multiple of the clipping norm, is 1.

The true \(\varepsilon\) lies between the two PLD columns, because the lower PLD column is a lower bound. Advanced composition, which adds up the guarantees of the steps, is useless here. RDP is much closer, but it still overstates \(\varepsilon\), by 14.6% on the shorter run and by 7.6% on the longer one. This gives the rule of the chapter. Report the tightest upper bound whose assumptions hold for the code you ran, and give enough detail that someone else can recompute it.

25.2 Which accountant

An accountant is tight only when its summary of each step fits the mechanism. So let the mechanism choose the accountant (Table 25.2).

The GDP CLT is an approximation, not a bound. After 1,000 steps it gives 1.6177, which is below the certified lower value of the PLD, 1.8232. So it claims a guarantee that the run does not have. Opacus’s "gdp" accountant is this CLT, so do not report it. The default PRV accountant of Opacus is safe.

25.3 The inverse problem: noise for a target ε

Usually you fix the target \(\varepsilon\), the batch size and the number of epochs, and you ask for the smallest \(\sigma\) that meets them. A looser accountant overstates \(\varepsilon\), so it asks for more noise. For a target of 3 on the 10,000-step run, RDP needs a noise multiplier of 1.662 and the PLD only 1.584. So calibrate with the accountant that you will report. Opacus’s get_noise_multiplier uses "rdp" by default, so give it accountant="prv" (Calibrate and account a DP-SGD run).

25.4 Choosing δ

Choose \(\delta\) by the rule of this book, which for \(n\) people is at most \(1/n^{1.1}\), rounded down to a power of ten (How small δ must be). Count \(n\) in the unit that the claim protects, which at the user level means users, not records. For example, run the 10,000 steps of Table 25.1 on 50,000 records. At \(q = 0.01\), that is 100 epochs. For 50,000 records the rule gives \(10^{-6}\), so the \(10^{-5}\) of the table fails it. The US National Institute of Standards and Technology (NIST) recommends the stricter \(1/n^2\), so report \(\varepsilon\) there too.

Publish the upper value of the accountant that you name, rounded up, because the accountant does not certify a lower value. Write the statement shows the full privacy statement that carries these numbers.

25.5 Matching the accountant to the code

The number of an accountant holds only if the code does what its theorem assumes. Many papers reported the number for Poisson sampling but trained with shuffled batches of fixed size, a different algorithm (Ponomareva et al. 2023). So check the code against Table 25.3 before you report.

The sampler has the largest effect. Under Poisson sampling, the PLD of dp_accounting gives 6.19 at \(\delta = 10^{-5}\), but batches of fixed size raise this to 43.37. Shuffle and partition raise it to 91.82, and that number holds only for zero-out neighbours (Subsampling).

A review of someone else’s claim also uses this checklist, in the order that Review someone else’s claim gives.

25.6 Checking an accountant

An accountant is code, so test it on known answers. With sampling rate \(q = 1\), each step is a plain Gaussian mechanism, and the composition of such steps is exact (f-DP and Gaussian DP). Ten such steps at noise multiplier 1 are exactly \((17.8566, 10^{-5})\)-DP. So an upper bound must be above 17.8566, and a PLD bracket must contain it. Also, \(\varepsilon\) must not decrease when you add steps, and it must not increase when you add noise.

Then compare two maintained libraries at pinned versions. This snippet recomputes Table 25.1 with Google’s dp_accounting.

import dp_accounting
from dp_accounting.pld import PLDAccountant
from dp_accounting.rdp import RdpAccountant

step = dp_accounting.PoissonSampledDpEvent(0.01, dp_accounting.GaussianDpEvent(1.0))
run = dp_accounting.SelfComposedDpEvent(step, 10_000)  # q = 0.01, sigma = 1, 10,000 steps
pld = PLDAccountant(value_discretization_interval=1e-4).compose(run)
rdp = RdpAccountant(orders=list(range(2, 65))).compose(run)  # integer orders only
print(f"{pld.get_epsilon(1e-5):.4f} {rdp.get_epsilon(1e-5):.4f}")  # 6.1877 6.7194
print(f"{pld.get_epsilon(1e-6):.4f} {rdp.get_epsilon(1e-6):.4f}")  # 6.9074 7.4869

Each PLD value is inside the bracket of the table. Each RDP value is just above the value in the table, because the table also tries fractional orders. When libraries disagree, look for three causes. If two RDP values differ by an amount that depends only on the order, such as 0.3612 at order 10, the libraries use different conversions (RDP conversions). If two PLD brackets do not overlap, one library has a bug. A factor of two often comes from different neighbouring relations.
