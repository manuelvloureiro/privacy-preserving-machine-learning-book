8.1 Why this matters

In federated learning (FL), a server sends the current model to each phone or other client. The client computes the gradient of the loss on its own few records and sends back only that gradient. The server averages the gradients and takes a training step. People often call this private because “the data stay on the device”.

Yet one client’s gradient can give back all of that client’s data, because many of its derivatives are simple functions of the input. An average over a batch protects much less than people expect (Section 8.6). So treat each client’s update as being as sensitive as the data it came from.

8.2 The attacker and what it sees

The attacker is the server, which knows every parameter because it sent the model out, and which also sees each client’s own update. So its access is the transcript of Threat models and privacy games, everything that training exposes. Assume first that the server is honest-but-curious, so that it only analyses what it receives. Each client holds a batch of \(B\) records and sends the average of their gradients. Write \(\ell_i\) for the loss on record \(i\), which depends on all the parameters \(\theta\). The client then sends \[g = \frac1B\sum_{i=1}^B\nabla_\theta\ell_i. \tag{8.1}\]

8.3 Exact recovery from a fully connected layer

The most common first layer, a fully connected layer with a bias, gives its input back by one division. Write \(W_1\) and \(b_1\) for its weights and bias. Each unit \(j\) multiplies the input \(x\) by its row of weights and adds its bias. Its backward signal \(u_j\) is how fast the loss responds to the unit’s output. The chain rule turns this signal into the weight and bias gradients \[\nabla_{W_1}\ell = u\,x^\top, \qquad \nabla_{b_1}\ell = u. \tag{8.2}\] So row \(j\) of the weight gradient is the input scaled by \(u_j\), and the bias gradient of unit \(j\) is that same scale. For a single record, divide one by the other. This gives the input exactly, for every unit whose bias gradient is not zero: \[x = \frac{(\nabla_{W_1}\ell)_{j,:}}{(\nabla_{b_1}\ell)_j}. \tag{8.3}\]

Everything above the layer, including the network’s depth, the loss and the label, sits inside \(u_j\) and cancels. So the attack needs no optimization and no knowledge of the data. The snippet below plays one client with one image of scikit-learn’s digits in PyTorch. Its last line reads the label, as Section 8.4 explains.

import torch
import torch.nn.functional as F
from sklearn.datasets import load_digits

torch.manual_seed(0)
images, labels = load_digits(return_X_y=True)
x = torch.tensor(images[[7]] / 16, dtype=torch.float32)  # one client's image, pixels in [0, 1]
y = torch.tensor(labels[[7]])
first, last = torch.nn.Linear(64, 32), torch.nn.Linear(32, 10)
F.cross_entropy(last(torch.relu(first(x))), y).backward()  # the gradient the client sends
# Row j of the weight gradient is the input times the bias gradient of unit j: divide them.
j = int(first.bias.grad.abs().argmax())
recovered = first.weight.grad[j] / first.bias.grad[j]
print(f"image recovered: {torch.allclose(recovered, x[0], atol=1e-6)}")  # image recovered: True
# Only the true label's logit has a negative gradient (softmax minus one-hot).
print(f"recovered label {int(last.bias.grad.argmin())}, true label {int(y)}")  # recovered label 7, true label 7

The snippet divides at the unit whose bias gradient is largest, because a ReLU unit that is off has a zero gradient. One active unit is enough. But a convolutional first layer stops the division. It uses the same filter at every position of the image, so its gradient is a sum of one product per image patch. No division can separate them. The attacker then has to search (Section 8.5).

8.4 Label recovery from the last layer

The label is often the most sensitive part of an example, such as a diagnosis. The attacker can read it off the last layer without search (Zhao, Mopuri & Bilen 2020). The condition is that the layer has a bias and feeds the softmax and cross-entropy loss. Write \(p\) for the predicted probabilities and \(e_y\) for the vector with a 1 at the position of the label \(y\). The gradient of the last layer’s bias \(b_2\) is then \(p - e_y\). Every entry of \(p\) lies between 0 and 1, so only the entry at the true label is negative, and for a single record \[y = \arg\min_k(\nabla_{b_2}\ell)_k, \tag{8.4}\] which is the snippet’s argmin. It fails only for a very confident model. If the true label’s probability \(p_y\) rounds to 1, that entry becomes zero, and no entry is negative.

A batch hides which record has which label, but not how many records each class has. Each entry of the bias gradient is then the class’s average predicted probability minus its share of the batch. So a server that estimates the average prediction can read off each class’s count. In the full edition’s experiment, this gave every count exactly in all batches of 4, and in 52.5% of batches of 64.

8.5 Deep Leakage from Gradients

When the division does not apply, the attacker searches. Deep Leakage from Gradients (DLG), from Zhu, Liu & Han (2019), guesses inputs and computes the gradient they would produce. It then moves the guesses until that gradient matches the observed gradient \(g\). Write \(x_i'\) for the guessed inputs, \(y_i\) for their labels, read first from the last layer, and \(\ell(\theta; x', y)\) for the loss of one guess. The attack minimizes the matching loss \(R\), the squared distance between the guesses’ average gradient and \(g\): \[\hat x_1, \dots, \hat x_B = \arg\min_{x_1', \dots, x_B'}R(x'), \qquad R(x') = \Big\|\frac1B\sum_{i=1}^B\nabla_\theta\ell(\theta; x_i', y_i) - g\Big\|^2. \tag{8.5}\] In PyTorch, create_graph=True in torch.autograd.grad makes the guess’s gradient differentiable, so an optimizer such as Adam can follow the slope of \(R\) back to the input.

Two things decide whether the search works. First, the activation’s slope must vary, because the search differentiates a gradient. The ReLU’s slope is constant on each side of zero, so Zhu et al. used the sigmoid. Second, \(R\) is not convex, so the search can get stuck. Run it until \(R\) stops falling, and compare the final value with the squared size \(\|g\|^2\) of the observed gradient. In double precision, a successful run in the full edition ends near \(10^{-27}\) and a stuck one near \(10^{-5}\). Another input can also give a small \(R\), so restart from several random guesses, and trust an image only when the restarts agree on it.

8.6 Batches and averaging

Clients usually send the average over a batch, or the change in their parameters after several training steps on the device (local steps). The average breaks the division and slows the search, but much of the structure survives. Each record adds one outer product to the gradient of the first layer, so every row of that gradient is a combination of the \(B\) inputs. So the server learns their span, the set of all such combinations, which contains every record.

The division still recovers a record exactly when some ReLU unit is on for that record only. The other records then add nothing to that unit’s row. Such a unit isolates the record. Isolation is far more common than a count of random units suggests. On images that resemble one another, a unit fires on many records or on few. In the full edition’s network with 1,024 hidden units, a naive count predicts that 1.6% of a batch of 16 is exposed. But 69.1% was, as Table 8.1 shows. The share falls with a larger batch and rises with a wider first layer. So measure at your own width and batch size, and treat any isolated record as a breach.

Batches hurt DLG more: on the full edition’s sigmoid network, the median run on a batch of 4 gets stuck. The search is harder, but the information is still there, because the isolation attack recovered all four images of such a batch. Local steps do not protect a single record either. The gradient of the first layer at each step is an outer product with the same input, so the division still works on the total change. A malicious server that chooses the weights can do more. It plants units that fire only on rare inputs, so that each unit isolates one record. It then recovers most records of a batch of any size (Boenisch et al. 2023, Fowl et al. 2022).

8.7 What to do as a deployer

The risk of an FL deployment depends on who can see one client’s update, as Table 8.2 shows.

Secure aggregation is a cryptographic protocol that lets the server see only the sum over many clients. It removes the view of single clients that every attack here uses. But a sum over very few clients is close to a single update. So set a minimum cohort size, and make sure that clients who drop out in a round cannot shrink a sum below it.

Secure aggregation alone is not enough. The sum is still a batch average that the attacks above can read, and a malicious server can still choose its weights. For a guarantee, add DP with the client as the unit of privacy. Clip each client’s update to a fixed maximum norm and add noise to the sum. That bounds what any one client’s data can change (User-level privacy). Flower and TensorFlow Federated offer both protections. Gradient pruning and similar defences make the search harder but give no guarantee.

To assess your deployment, first find out whether the server sees single updates or only sums, and with what minimum cohort. Then run the attacks on your own architecture, batch size and number of local steps. Geiping’s open-source breaching framework for PyTorch runs them. If the server can see one client’s update on its own, block the deployment until secure aggregation or client-level DP is in place. Record the verdict in the Pre-release privacy risk assessment.

8.8 Cheat sheet

Rules of thumb

  • Secure aggregation needs a minimum cohort, and only client-level DP bounds what any update reveals.
